# Verification of #329 on a real x86-64 Linux host

Date: 2026-11-04
Host: `evo2` (EVO-X2, Ubuntu 24.04, kernel 7.0.0-42, 32 threads, 30 GiB, x86-64), exclusive, no MKL, no OpenBLAS, no pip/venv, no GPU, no Julia.
Harness: `tensor4all/tenferro-benchmark`, `main` @ `54c32f6`, plus a second worktree at `0baddde` (the revision the red 11-03 nightly ran).
`kache doctor --verify`: all checks passed, 0 cache entries.

This records what was reproduced on real hardware. #330 and #331 landed before this
run, so the red state was reproduced at `0baddde` and then compared against `main`.

## Environment substitution

The nightly collection step runs inside the MKL devcontainer:

```bash
export TENFERRO_CPU_FEATURES=blas-mkl PUBLICATION_GATE_FEATURES=blas-mkl
export BENCHMARK_TARGET_PROFILE=amd-cpu PUBLICATION_GATE_PROFILE=quick
export BENCHMARK_ALLOW_BUSY_HOST=1 PERMUTATION_EXTRA_FEATURES=hptt
./scripts/run_all.sh 1 4
```

This host has no BLAS at all, so `TENFERRO_CPU_FEATURES=native` (the crate's own
default, `tenferro-cpu/native` on faer) replaces `blas-mkl`. That substitution does not
touch the failure under investigation, which happens before any measurement, but it does
mean the MKL-backed rows and the MKL build cannot be exercised here.

`run_all.sh` also needs `campaign_toolkit` (a `uv` git dependency). Without pip or uv it
was made importable the plain way:

```bash
git clone https://github.com/tensor4all/campaign-toolkit ~/work/campaign-toolkit
cd ~/work/campaign-toolkit && git checkout 20029055ba42fe07dd13a69052b097a5083c46da
export PYTHONPATH=$HOME/work/campaign-toolkit
```

## A. Missing MWE binary — reproduced at `0baddde`

`BENCH_INSTANCE` is consumed globally, so it cannot be narrowed to the `perf_issues`
suite through `run_all.sh` (the einsum suite rejects ids it does not know and exits
first). The reproduction therefore uses the script `run_all.sh:107` invokes, with the
remaining suites switched off:

```bash
export RUSTC_WRAPPER= TENFERRO_CPU_FEATURES=native BENCHMARK_TARGET_PROFILE=amd-cpu \
       PUBLICATION_GATE_PROFILE=quick BENCHMARK_ALLOW_BUSY_HOST=1 BENCH_COVERAGE=quick \
       BENCH_INSTANCE=followup_perm_reverse_15d_3_materialize,followup_perm_reverse_23d_2_strided-rs,followup_perm_transpose_3d_256_201_materialize
./scripts/run_perf_issues.sh 1
```

Three cases whose reference arm is also a Rust path, so nothing but the missing binary
can fail:

```text
followup_perm_reverse_15d_3_materialize: failed
followup_perm_reverse_23d_2_strided-rs: failed
followup_perm_transpose_3d_256_201_materialize: failed
Case status t1: executed=0 failed=3 skipped=0 missing=0
exit=1
```

The recorded row error, byte for byte the string from the 11-03 nightly:

```text
FileNotFoundError(2, 'No such file or directory')
```

Exit-code path, with the same `set -euo pipefail` `run_all.sh` uses:

```bash
$ (set -euo pipefail; ./scripts/run_perf_issues.sh 1 >/dev/null 2>&1; echo "NOT REACHED"); echo "exit=$?"
exit=1
```

so `run_perf_issues.sh`'s closing `exit "$failed"` reaches `run_all.sh`, which is what the
nightly log reports as `CPU collection failed at line 16: ./scripts/run_all.sh 1 4`.

Ordering note: the reference arm runs **before** the Rust arm
(`cpu_followup_cases.run()`), so on the nightly the `pytorch` reference succeeds, the
`eager-shared`/`direct-shared` MWE call then raises, and that error is what the row
records. On this host the reference arm itself is unavailable for most cases, which is
why the slice above was restricted to the 16 fully-Rust cases.

## A2. The path is not mismatched; the build is simply absent

- Collector default, unchanged since before the fix
  (`git show 0baddde:scripts/cpu_followup_cases.py:36`):
  `str(ROOT/'target/followup-current/release/cpu-followup-mwe')`
- Build: `build_followup_mwe()` in `scripts/run_cpu_followup.sh` exports
  `CARGO_TARGET_DIR="$PWD/target/followup-current"` and builds
  `mwe/cpu_followup/Cargo.toml`; the collector reads `ROOT/target/followup-current`.
  One directory, one writer.
- What the nightly leaves unbuilt: nothing on the `run_all.sh` → `run_perf_issues.sh`
  path called that builder before #330. `ls target/followup-current/release/cpu-followup-mwe`
  → `No such file or directory`.

Proven live on `main`, which prints the absolute path it resolves:

```text
RuntimeError('CPU follow-up MWE binary is missing: /home/shinaoka/work/tenferro-benchmark-329/target/followup-current/release/cpu-followup-mwe. Build it with `./scripts/run_cpu_followup.sh --prepare-mwe` (or `CARGO_TARGET_DIR="$PWD/target/followup-current" cargo build --release --manifest-path mwe/cpu_followup/Cargo.toml`); the nightly path builds it through `./scripts/run_cpu_followup.sh --prepare-mwe`. `CPU_FOLLOWUP_BIN` overrides the location.')
```

### The build itself cannot be exercised on this host

Exactly what `--prepare` runs:

```bash
$ CARGO_TARGET_DIR="$PWD/target/followup-current" cargo build --release --locked --manifest-path mwe/cpu_followup/Cargo.toml
  thread 'main' (110037) panicked at build.rs:4:54:
  MKLROOT required: NotPresent
```

and without a provider:

```bash
$ ... --no-default-features
error: tenferro-linalg needs exactly one CPU backend: enable the `native` (default) or `blas` feature
   (91 errors total)
```

`mwe/cpu_followup` selects its provider only through `system-mkl` / `system-openblas`, and
this host has neither, so the MWE cannot be built here and "which rows turn green once the
binary exists" is **not** verified. What is verified is everything short of that: the
resolved path, the build command, and the fact that the absence of that one file is the
sole cause of the three rows failing.

## B. `cpu_ops` inventory drift — reproduced, and the commit is identified

Declared inventory at the red nightly (`git show 0baddde:benchmarks/cpu/ingestion-selection.json`):
`cpu/cpu_ops = 892`, `cpu/linalg_jvp_vjp = 300`, `threads = [1, 4]`.

The 11-03 CSVs (from artifact `41687773887`), measured with the repository's own
formatters:

```text
  t1: cpu_ops identities=496  linalg identities=200
  t4: cpu_ops identities=496  linalg identities=200
  cpu/cpu_ops total across the two thread counts = 992
  cpu/linalg_jvp_vjp total                       = 400
```

992 against 892 and 400 against 300: the same +100 in both, i.e. +50 rows per thread.

Which commit moved them: `e479872` — *cpu/publication_gate: measure linalg JVP/VJP on the
eager arm (#311)*, 2026-11-02, the day before the first red nightly. Its diff registers
exactly ten ids on the eager arm:

```text
grad_sum_{svd_s,qr,eigh,lu,solve}_{jvp,vjp}
```

10 ids × 5 shapes × 2 thread counts = 100 new identities, which is the observed delta.
It also reconciles with the last green run: the 10-29 `cpu_ops` CSV in artifact
`12948690465` held 446 rows per thread, and 446 + 50 = 496.

So the row change was intended (#311 widened the eager arm) and the declaration was stale.
`main` now declares 992 / 400 after #331 (`git show a3d634d:benchmarks/cpu/ingestion-selection.json`).
The generator #331 added (`scripts/ci/generate_cpu_ingestion_selection.py`) was not run
here: it needs a packaged collection and this host cannot produce one.

## Open, not verified here

- That the MWE builds and validates against the pinned tenferro revision under
  `system-mkl`, and that the 94 rows pass once it exists. Needs MKL.
- The `julia-base`, `jax` and `mkl-dfti` reference arms: no Julia and no numpy/torch/jax
  here, so those rows never reached their reference runner.
- The mac nightly end to end. On Darwin `followup_mwe_supported()` returns false and the
  rows are skipped, which reads correctly in code and in
  `test_unsupported_host_skips_before_any_process`, but it was not executed.
- Whether the 2026-11-05 linux nightly is green.

## One asymmetry found

`followup_mwe_supported()` returns true on any Linux, while the builder's precondition is
`MKLROOT/include`. A Linux host with no MKL therefore still records 94 failures per thread
count — observed here — where macOS records skips. Whether that is intended (fail loudly
on a misconfigured Linux collector) or an oversight is a maintainer decision; it is not
changed here.

## Documentation correction

`docs/worklogs/2026-11-04-linux-cpu-ops-triage.md` says `run()` in
`cpu_followup_cases.py` "executes the *Rust* arm first". The code executes the reference
arm first and the Rust arm second; the row records the Rust arm's error only because the
reference arm succeeded first. Observed directly on this host: the case whose reference is
`jax` failed with `ModuleNotFoundError: No module named 'numpy'` from `reference.py`, not
with the MWE error. The conclusion of that document is unaffected — the missing binary is
why every arm fails — and the sentence is corrected in this PR.
